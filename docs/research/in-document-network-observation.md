## Summary

1. Playwright fills `Request`/`Response` from the browser's network layer; an in-document `fetch`/XHR wrapper sees only what the page script itself passed in and what the Fetch/XHR APIs expose back.
2. A wrapper can honestly give: `url`, `method`, author-set headers, `postData` for non-stream bodies, `resourceType` (`fetch`/`xhr` by construction), `status`, `statusText`, `ok`, exposed response headers, body via `clone()`, and the four events for `fetch()` and XHR only.
3. A wrapper cannot give: wire headers (`allHeaders`), `Set-Cookie`, headers on opaque responses, `timing` breakdown, `failure().errorText` as a `net::` code, `serviceWorker`, `sizes` beyond `Content-Length`, `httpVersion`, `serverAddr`, `securityDetails`, `redirectedFrom`/`redirectedTo` chains, `frame`, or any non-fetch/XHR resource.
4. `PerformanceObserver` needs no patch and covers every `initiatorType` (images, scripts, CSS, beacons, ...), but each entry arrives only after the response body ends, carries no headers or body, has `responseStatus` in Chrome 109+/Firefox 129+ and not Safari, and masks timing for cross-origin resources without `Timing-Allow-Origin`.
5. `fetch` is a writable, configurable own property of `window` (Web IDL), so replacing it is an ordinary assignment; a plain wrapper loses `name`/`length`/`toString` identity, a callable `Proxy` keeps them; either must forward `this` as `undefined` or `window` or the native call throws `TypeError`.
6. The pinned client's `waitForRequest`/`waitForResponse` use the same `urlMatches(baseURL, url, match)` as `waitForURL`; playwright-lite already carries a pinned copy of that matcher and glob grammar in `src/page.ts`.
7. The two pinned wait-for specs are in playwright-lite's corpus today as expected failures; all 12 of their positive tests fire `fetch()` after a setup `goto`.

## 1. Playwright's surface, and what wrappers can populate

### How the pinned client populates the fields

- The server creates `Request` with `url` (fragment stripped, `stripFragmentFromUrl`, server/network.ts L210), `resourceType`, `method`, `postData`, provisional `headers`, `frame`, `serviceWorker`, `redirectedFrom`, and asserts `data:` URLs never fire requests (L204). `resourceType` is the rendering engine's classification (`ResourceType`, L156-172; public doc types.d.ts L22027-22031).
- The client `Request` returns those initializer values synchronously (`url` L127, `resourceType` L131, `method` L135, `postData` L139-149, `headers` L171 marked `@deprecated`, provisional), while `allHeaders`/`headersArray`/`headerValue` go back to the driver for the raw wire headers (`rawRequestHeaders`, L177-199).
- `timing()` starts as `{startTime: 0, others: -1}` (L114-124); the server-side timing is copied in when the `Response` is constructed (L670) and `responseEnd` is set on `requestfinished`/`requestfailed` (browserContext.ts L213-231, `_setResponseEndTiming` L268-272). Public doc: "Most of the timing values become available upon the response, `responseEnd` becomes available when request finishes" (types.d.ts L22080-22082). Memory-cache hits get `requestStart = responseEnd` (server/network.ts L583-585).
- `failure()` returns `{errorText}` only after `requestfailed` set `_failureText` (L249-255, browserContext.ts L214). Public doc: HTTP errors such as 404 are `requestfinished`, not `requestfailed`; failure means "the client cannot get an HTTP response from the server, e.g. due to network error net::ERR_FAILED" (types.d.ts L1150-1165).
- Events: `request`, `response`, `requestfinished`, `requestfailed` are emitted on the `BrowserContext` and re-emitted on the owning `Page` with the same `Request`/`Response` objects (browserContext.ts L201-231; names events.ts L58-61). Documented order for a success: `request`, `response`, `requestfinished` (types.d.ts L1168-1171).
- `Response`: `url`, `status`, `statusText`, `ok` (status 0 counts as ok for `file:`), `fromServiceWorker`, provisional `headers` are synchronous (L674-700); `allHeaders`/`headersArray`/`headerValue`/`headerValues`, `body`/`text`/`json`, `serverAddr`, `securityDetails`, `httpVersion` are driver round-trips (L702-763); `finished()` resolves on `requestfinished` (L727, browserContext.ts L231).

### Resource types each observer sees

- fetch wrapper: only `fetch()` calls made from this realm through the patched property (workers, service workers, iframes and other realms have their own `fetch`). Not seen: images, scripts, stylesheets, fonts, media, `navigator.sendBeacon` (initiator `beacon`), `WebSocket`, `EventSource`, `<a ping>`, `<link rel=preload>`, form submissions, navigations, `fetchLater`.
- XHR wrapper: only `XMLHttpRequest` from this realm.
- PO: every fetch that has an initiator type ([Fetch: mark resource timing only "if request's initiator type is non-null"](https://fetch.spec.whatwg.org/#request-initiator-type)); the `initiatorType` list above has no `websocket` or `eventsource` value. Whether those produce `other` entries is not settled by the spec text read here.

## 2. What `PerformanceObserver` provides without patching

- **Fields** ([IDL](https://w3c.github.io/resource-timing/#sec-performanceresourcetiming)): `name`, `entryType` (`"resource"`), `startTime`, `duration`, `initiatorType`, `deliveryType`, `nextHopProtocol`, `workerStart`, `redirectStart`, `redirectEnd`, `fetchStart`, `domainLookupStart`, `domainLookupEnd`, `connectStart`, `connectEnd`, `secureConnectionStart`, `requestStart`, `finalResponseHeadersStart`, `firstInterimResponseStart`, `responseStart`, `responseEnd`, `workerRouterEvaluationStart`, `workerCacheLookupStart`, `workerMatchedRouterSource`, `workerFinalRouterSource`, `transferSize`, `encodedBodySize`, `decodedBodySize`, `responseStatus`, `renderBlockingStatus`, `contentType`, `contentEncoding`, `serverTiming`. No method, headers, body, error text, or final URL.
- **When**: the entry is created by "mark resource timing", which Fetch runs inside its report-timing steps at `processResponseEndOfBody`, i.e. after the body has been fully transmitted, or immediately when the body is null (including network errors) ([Fetch response handover](https://fetch.spec.whatwg.org/#fetch-finale)). There is no per-request start notification. Delivery to observers is a queued task on the performance timeline task source, coalesced per global by the "performance observer task queued" flag ([Performance Timeline §5.3](https://w3c.github.io/performance-timeline/#dfn-queue-the-performanceobserver-task)), so callbacks are asynchronous and batched.
- **`responseStatus` per browser** (BCD `c800c48`): Chrome 109, Firefox 129, Safari `false` (not supported). Value 0 for cross-origin `no-cors` responses ([RT](https://w3c.github.io/resource-timing/#dom-performanceresourcetiming-responsestatus)); for non-navigation requests Fetch sets it to the response status when the request mode is not `navigate` or the redirect taint is same-origin ([Fetch report timing steps](https://fetch.spec.whatwg.org/#fetch-finale)).
- **Buffer limits**: the resource timing buffer size limit is "initially 250 or greater"; when it is full, entries go to a secondary buffer and `resourcetimingbufferfull` fires; `performance.setResourceTimingBufferSize()` and `clearResourceTimings()` control it ([RT §3.4](https://w3c.github.io/resource-timing/#sec-extensions-performance-interface)). A *live* observer is not limited by that buffer: "queue a PerformanceEntry" appends to every interested observer's buffer before checking whether the global buffer is full ([Performance Timeline §5.1](https://w3c.github.io/performance-timeline/#queue-a-performanceentry)). `observe({type: "resource", buffered: true})` replays only what is still in the global buffer ([`observe()`](https://w3c.github.io/performance-timeline/#dom-performanceobserver-observe), [`buffered`](https://w3c.github.io/performance-timeline/#dom-performanceobserverinit-buffered)).
- **Cross-origin without `Timing-Allow-Origin`**: the entry is opaque; `redirectStart`, `redirectEnd`, `workerStart`, `domainLookupStart`, `domainLookupEnd`, `connectStart`, `connectEnd`, `requestStart`, `firstInterimResponseStart`, `finalResponseHeadersStart`, `responseStart`, `secureConnectionStart` return 0 and `nextHopProtocol` the empty string; `contentType`, `encodedBodySize`, `decodedBodySize` are zero/empty when the response is CORS-cross-origin ([RT §3.5.1](https://w3c.github.io/resource-timing/#sec-cross-origin-resources)). `startTime`, `fetchStart`, `responseEnd`, `duration` and `name` remain. The UA may zero the sizes even with TAO ([RT §3.5.2](https://w3c.github.io/resource-timing/#sec-timing-allow-origin)). TAO is supported in Chrome 54, Firefox 45, Safari 11 (BCD).

## 3. Wrapping technique

### Where `fetch` and XHR live

- `fetch` is a regular operation of the `WindowOrWorkerGlobalScope` mixin ([Fetch §5.6](https://fetch.spec.whatwg.org/#dom-global-fetch)). Because `Window` is `[Global]`, regular operations are defined as own properties of the global object itself, not of a prototype ([Web IDL "Operations"](https://webidl.spec.whatwg.org/#es-operations)), with `{[[Writable]]: true, [[Enumerable]]: true, [[Configurable]]: true}` for non-unforgeable operations ([define the operations](https://webidl.spec.whatwg.org/#define-the-operations)). So `window.fetch = wrapper` is an ordinary data-property assignment, and `fetch`, `window.fetch`, `globalThis.fetch`, `self.fetch` all resolve to it in that realm.
- `XMLHttpRequest` operations live on `XMLHttpRequest.prototype` with the same attributes, so `open`, `setRequestHeader`, `send` can be replaced per prototype.

### `this` binding

Web IDL's operation function computes its receiver as: the `this` value if it is not `null`/`undefined`, otherwise the realm's global object; then, if the receiver does not implement the interface, it throws `TypeError` ([create an operation function](https://webidl.spec.whatwg.org/#dfn-create-operation-function)). Consequences:

- A wrapper must call the original with `this` as `undefined`, `window`, or `globalThis`. Forwarding whatever `this` the caller used (Ayde does `origFetch.apply(this, args)`) preserves native behaviour exactly, including the `TypeError` for a wrong receiver.
- Any wrapper that exposes the native `fetch` through a `Proxy` as *receiver* (a proxied `window`) makes the native call throw, because the Proxy is not a platform object implementing `Window`.

### Identity: `toString`, `name`, `length`

- Native: `Function.prototype.toString` on a built-in returns a `NativeFunction` string whose name portion must be the function's `[[InitialName]]`, i.e. `function fetch() { [native code] }` ([ECMA-262 §20.2.3.5](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function.prototype.tostring)). `fetch.name === "fetch"`, `fetch.length === 1` (one required parameter).
- Plain wrapper: `toString` returns its source text. Assigning an anonymous function expression to a *property* does not name it: NamedEvaluation applies only when the left-hand side is an identifier reference ([ECMA-262 assignment evaluation](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-assignment-operators-runtime-semantics-evaluation)). Ayde's `window.fetch = function (...args) {...}` therefore has `name === ""` and `length === 0` (rest parameter). `Object.defineProperty` can set `name` and `length` (both configurable, non-writable) but not `toString`'s output.
- Callable `Proxy`: `typeof` is `"function"`; `Function.prototype.toString` returns an implementation-defined `NativeFunction` string for any callable object without `[[SourceText]]` ([§20.2.3.5 step 3](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-function.prototype.tostring)); `name` and `length` are forwarded to the target by the default `[[Get]]`. So a `Proxy` with only an `apply` trap passes `toString`/`name`/`length` checks that a plain wrapper fails, at the cost of every property access going through the proxy. `proxy !== nativeFetch` for both techniques.

### `Request`-object inputs and bodies

- `fetch(input, init)` itself begins by constructing `new Request(input, init)` ([Fetch `fetch()`](https://fetch.spec.whatwg.org/#dom-global-fetch)). A wrapper that does the same gets normalized `url`, `method`, `headers`, and `signal` for free and must then pass *that* `Request` to the native call: constructing from a `Request` input that has a body sets the new body to a proxy of the input's stream ([Fetch `Request` constructor](https://fetch.spec.whatwg.org/#dom-request)), after which the original input is unusable and would make the native call throw `TypeError` ([unusable](https://fetch.spec.whatwg.org/#body-unusable)). Inference from the spec text; not exercised here.
- Reading a body without consuming it requires `clone()`, which tees the stream ([clone a body](https://fetch.spec.whatwg.org/#concept-body-clone)); the un-read branch buffers the whole body.
- Requests made by a service worker are not visible to the page's `fetch`; page requests answered by a service worker still go through the page's `fetch()` and are visible, and `PerformanceResourceTiming.workerStart` marks them.

### Restoring on dispose when the Site wrapped `fetch` after us

Facts that constrain a dispose:

- After `window.fetch = ours` and later `window.fetch = theirs`, `theirs` closes over `ours`. Restoring `window.fetch = native` removes the Site's wrapper; leaving `window.fetch` alone keeps `ours` alive inside `theirs`. The property is a plain data property, so no hook exists to detect the second assignment except making it an accessor (`Object.defineProperty` with `get`/`set`), which changes what `Object.getOwnPropertyDescriptor(window, "fetch")` reports.
- Ayde's guard `if (!w.__aydeNet)` (ayde.ts L17) prevents double installation on re-injection and never restores.

### Failure modes derivable from the sources

- Ayde XHR wrapper (ayde.ts L24-29) increments `inFlight` before calling native `send`; `send()` throws `InvalidStateError` when the object is not opened or was already sent ([XHR `send()`](https://xhr.spec.whatwg.org/#the-send()-method)), and `loadend` never fires for that call, so the counter leaks by one. Inference from the two texts; not observed in the Ayde results.
- Ayde fetch wrapper (L20-23): `origFetch.apply(this, args)` throws synchronously on a wrong receiver (Web IDL, above); the `inFlight++` before it then never decrements. Same status: inferred, not observed.
- Long polls and analytics beacons keep a request in flight; Ayde caps the wait at 4 s because of them (README "Settle misses network content", L162).
- Fragment: a wrapper reporting `Request.url` verbatim differs from Playwright, which strips the fragment (server L210).

### Ayde evidence, as recorded

The README evaluates 9 Sites × 3 goals with the wrapper active in `v1`/`v2` (README L5, L52, L68-77) and probed 18 candidate Sites, of which 6 served a bot-protection page on first load (L181). The recorded failure modes (L179-197) are bot protection, Jev input limits, overlays intercepting clicks, click stability, menu oscillation, off-Site targets and grader limits; none is attributed to the `fetch`/XHR wrappers. The figure "0 of 14 Sites broke" in #117 does not appear in the README; the README supports "no wrapper-attributed breakage on the 9 evaluated Sites (12 of 18 candidates loaded)".

## 4. URL matching in the pinned client and in playwright-lite

- `page.waitForRequest(urlOrPredicate)` / `page.waitForResponse(urlOrPredicate)` (client/page.ts L471-490): a string or `RegExp` is matched with `urlMatches(browserContext._options.baseURL, request.url(), urlOrPredicate)`; a function is awaited as a predicate on the `Request`/`Response` (not on a `URL`). The declared parameter type is `string | RegExp | ((r) => boolean | Promise<boolean>)`; `URLPattern` is not in that signature, although `urlMatches` accepts it. The wait itself is `_waitForEvent(Events.Page.Request | Response, {predicate, timeout, signal})`.
- `page.waitForURL(url)` (L467-469) takes `URLMatch = string | RegExp | ((url: URL) => boolean) | URLPattern` (urlMatch.ts L99) and delegates to `Frame.waitForURL` ([client/frame.ts](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/client/frame.ts) L197-199), which uses the same `urlMatches(baseURL, this.url(), url)`.
- `urlMatches(baseURL, urlString, match)` (urlMatch.ts L178-195): `undefined` or `""` matches everything; a string becomes `new RegExp(resolveGlobToRegexPattern(baseURL, match))`; a `RegExp` is tested with `lastIndex` reset; a `URLPattern` is tested against `href`; a function receives `new URL(urlString)` and gets `false` when the URL fails to parse. `resolveGlobBase` (L212-266) leaves globs that start with `*` alone, never resolves `about:`, `data:`, `chrome:`, `edge:`, `file:`, and resolves everything else against `baseURL` with `new URL(glob, baseURL)` after protecting glob metacharacters; `globToRegexPattern` (L30-93) anchors `^...$`, maps `*` to `[^/]*`, `**` to `.*` (with `/` handling), `{a,b}` to alternation, `?` literal-escaped.
- playwright-lite `src/page.ts` `urlMatches(url, match, ignoreCase, {emptyStringMatches})` (L4819-4839) is that algorithm with `baseURL` fixed to `undefined` (`resolveGlobToRegexPattern(undefined, match)`; there is no `baseURL` option on `createPage`), plus `ignoreCase` and `emptyStringMatches` for `expect(page).toHaveURL` (L596-603). It is used by `waitForURL`/`waitForLoadState` (L2449-2454) and carries pinned copies of `globToRegexPattern` (L4862), `resolveGlobToRegexPattern` (L4941), `resolveGlobBase` (L4949) and `resolveBaseURL` (L4999). The waitForRequest/waitForResponse form is `urlMatches(request.url(), match)` with the other two parameters left default.

## What this means for a decision

Facts only; no recommendation on whether to patch.

- Ledger rows involved (`compatibility/api.ts`): `waitForRequest`, `waitForResponse`, `request`, `route`, `routeFromHAR`, `routeWebSocket`, `unroute`, `unrouteAll`, `context` are `undecided`; `on`/`off`/`once`/`addListener`/`removeListener`/`waitForEvent` are `planned` under #116.
- The map's green test (3) forbids "patching of host-app globals". The `PerformanceObserver` path does not patch, and provides completion-only, header-less, body-less, `initiatorType`-classified entries (§2); it cannot produce `request` or `response` events or a `Request`/`Response` object with Playwright's synchronous fields. The `fetch`/XHR wrapper path does patch, and provides the four events and the fields marked available/partial in §1 for `fetch` and `xhr` resource types only.
- `tests/upstream/corpus.ts` already lists `page-wait-for-request.spec.ts` and `page-wait-for-response.spec.ts` (added in `9475a0a`; they run as expected failures since `08436f9`); `tests/upstream/baseline.json` has no entry from them. Of their 16 tests, 12 fire `fetch()` from `page.evaluate` after a setup `goto(server.EMPTY_PAGE)` and assert `request.url()`/`response.url()`; the other 4 assert timeout errors and log lines with no network. `page-event-request.spec.ts` (16 tests) needs navigations, iframes, service workers, `page.route`, `<img>`, and a 204 response; only "should fire for fetches", "should fire for fetches with keepalive: true", "main resource xhr should have type xhr" and "should return last requests" stay within fetch/XHR.
- README "Runtime boundaries" states "No network-idle observation. `networkidle` needs browser-wide request tracking, which this current-document runtime does not have." Neither observer in this report tracks requests browser-wide; the wrapper tracks one realm's `fetch`/XHR, the observer tracks one global's completed resources.
- The `urlMatches` helper needed by `waitForRequest`/`waitForResponse` already exists in `src/page.ts` in the pinned form; the remaining difference to the pinned client is the absent `baseURL`.
