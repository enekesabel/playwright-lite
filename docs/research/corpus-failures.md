# Corpus failures with implemented members

Research for [#190 "Which corpus tests fail although their members are implemented, and what would unlock them?"](https://github.com/enekesabel/playwright-lite/issues/190), measured on `main` at `51c63a3` against the pinned corpus (Playwright `26a9e470a7b3c7822084b09fb7f13902c5f37b51`, `@playwright/test` 1.62.1, Chromium).

## Verdict

`pnpm baseline:check` reports 2087 tests: 1165 candidate passes (1077 reviewed, 88 newly passing and owned by [#189](https://github.com/enekesabel/playwright-lite/issues/189)), 296 diagnostic passes, 10 skipped and **616 failures**.

- **279** failures use at least one member the ledger does not implement (Table A). They fail as expected.
- **337** failures use only `implemented` or `partial` members. Of these:
  - **202** fail on a limitation the project already documents: a README runtime boundary or the member's own ledger note (Table A2). Examples are cross-document navigation, file paths and synthetic input. They are expected in substance, but the ticket's status rule does not catch them.
  - **135** fail for a reason nothing documents (Table B). These are the subject of the ticket.

Of the 135, 41 need a test callback to run in Node. `AGENTS.md` "Harness trust" rules that out on purpose, so no fix unlocks them today. The other 94 split into 26 causes. The five that unlock the most are:

| Rank | Cause                                                                                                                                   | Tag     | Tests failing on it | Tests unlocked                         |
| ---: | --------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------: | -------------------------------------- |
|    1 | Specs that need `goto` only as setup are missing from `nativeNavigationForSetupSpecs`                                                   | harness |                  11 | **8** (verified)                       |
|    2 | The injected and evaluation scripts read page globals the page deleted or replaced (`Node`, `Event`, …)                                 | bug     |                  12 | **7** (verified), 8 with `URL`/`Date`  |
|    3 | `expect` call-log locator rendering and abort text ([#179](https://github.com/enekesabel/playwright-lite/issues/179), already ticketed) | bug     |                   8 | ≤ 8 (estimate)                         |
|    4 | Error text of `$eval`, `$()`, `selectText` and `waitForElementState` differs from the pinned text                                       | bug     |                   6 | ≤ 7 (estimate: 6, plus 1 from cause 1) |
|    5 | `waitForSelector` option-validation messages differ, and `waitFor: 'visible'` is rejected                                               | bug     |                   6 | 6 (estimate)                           |

"Verified" means a local prototype of the fix was run and the tests passed (see [Verification](#verification-experiments)). The prototype was reverted and nothing was committed. Every other unlock figure is an upper bound, read from the recorded failure and the spec source.

## Method

1. **Failing set.** `devbox run -- pnpm build`, then `devbox run -- pnpm baseline:check` on `main` `51c63a3`. The Playwright JSON report (`test-results/report.json`) gave each test's status, error, and `adapter-execution` annotation: members `entered`, `native` operations, transport `failures`, and `expectPaths`. A test counts as failing when its first result is neither `passed` nor `skipped`, the same rule `compareBaseline` in `scripts/upstream-baseline.mjs` uses.
2. **Members per test.** Each test's members are the union of three sources:
   - A static pass over the spec source with the TypeScript checker. It resolves every property access in the test body, its enclosing `beforeEach` hooks and local helpers (including `tests/config/utils.ts`) to its declaring Playwright interface, such as `Page.click`, `Mouse.move`, `ElementHandle.contentFrame` or `LocatorAssertions.toHaveText`. It also extracts the literal event name of every `on`/`once`/`waitForEvent` call.
   - The recorded public members: ledger rows among `entered`, all `native` operations, and the matchers in `expectPaths`.
   - Reading the test by hand when a member is reached through `any` or a computed name, for example `(expect(page) as any).toBeOK()` and `page[method]`. This moved 4 tests to Table A.
3. **Classification against the ledger** (`compatibility/api.ts`). Each member maps to its ledger row:
   - `Frame.x` maps to `Page.x`, because `mainFrame()` returns the Page. Frame-only members count as `out-of-scope`, because they need `frames()`.
   - `FrameLocator`, `BrowserContext`, `Route` and `APIRequestContext` count as `out-of-scope`.
   - `ElementHandle`, `Request` and `Response` members listed under "Not available" in `objectSections` count as not available.
   - An event name outside `events` counts as an unsupported event: `on`, `once` and `waitForEvent` are `partial` with the note "Fires only the supported events".
   - `selectors.register()`, `FileChooser` and `toImpl()` have no ledger row.
   - `setContent`, `setViewportSize`, `Browser.newContext`, `BrowserContext.newPage` and `BrowserContext.close` are `out-of-scope`, but the fixture runs them natively as document setup, and reviewed baseline entries pass with them in `native` evidence. They do not make a test expected. The same holds for `expect.soft`, which the corpus fixture serves through the test runner (`createCorpusExpect` in `tests/upstream/pageTest.ts`).
4. **Root cause.** I read every one of the 337 tests and the failing assertion, then gave each a single cause: the first failure observed. A test can have further failures behind it, and those are noted where known. Tags follow the ticket. Everything the project documents went to Table A2.
5. **Verification.** Harness causes 1 and 7, and adapter cause 2, were prototyped locally and rerun spec by spec, to replace estimates with observations.

Limits:

- The static pass cannot tell which browser branch runs, so a member used only in, for example, a `firefox` branch still counts. I checked the 20 expected tests whose error text names none of their unsupported members. That found the `expect.soft` misclassification, which I corrected. The rest are genuinely blocked, for example by an unsupported event whose native resolver cannot cross the bridge.
- Execution evidence is lost when the document navigates. The annotation is read from the new document, so `entered` is empty for the 116 cross-document tests.

## Top five: pinned behaviour and fix sketch

### 1. List the three setup-only specs for native setup navigation (harness, 8 tests)

**Pinned behaviour.** `Page.waitForRequest` and `waitForResponse` are client-side waits on `Request` and `Response` events ([`packages/playwright-core/src/client/page.ts#L471-L493`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/client/page.ts#L471-L493)). Each failing test only calls `page.goto(server.EMPTY_PAGE)` first, to get an http origin for `fetch()`. `selectors-frame` does the same before `$('iframe >> internal:control=enter-frame >> …')`.

**Fix.** Add `page-wait-for-request.spec.ts`, `page-wait-for-response.spec.ts` and `selectors-frame.spec.ts` to `nativeNavigationForSetupSpecs` in `tests/upstream/pageTest.ts`. **Size.** One `test:` harness PR. A harness PR promotes nothing; the promotion follows as its own step.

### 2. Snapshot page globals for the pinned scripts (bug, 7 tests verified)

**Pinned behaviour.** The injected script reads `Node` directly, for example `node.nodeType === Node.ELEMENT_NODE` in `retarget` ([`packages/injected/src/injectedScript.ts#L638-L639`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/injected/src/injectedScript.ts#L638-L639)). Playwright normally runs that script in the isolated utility world. When a browser has no utility world, it prefixes the injected and utility sources with `mainWorldGlobalsSnapshotSource`. That source rebinds `Node`, `Element`, `NodeFilter`, `HTMLElement`, `Document`, `ShadowRoot`, `MutationObserver`, `Event`, `CustomEvent`, `EventTarget`, `Map`, `Set`, `WeakMap`, `WeakSet`, `Promise`, `Symbol`, `Error`, `TypeError`, `RegExp`, `Array`, `Object`, `JSON` and `Math`. Each name takes the live global when it is still a function or object, and otherwise the copy that `saveGlobalsSnapshotSource` stored at page start ([`packages/playwright-core/src/server/javascript.ts#L365-L394`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/javascript.ts#L365-L394); used at [`server/dom.ts#L102-L107`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/dom.ts#L102-L107) and [`server/javascript.ts#L107`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/javascript.ts#L107)). The adapter evaluates the same sources in the page's main world with no snapshot (`build/playwrightInjectedPlugin.ts`), so a page that deletes `window.Node` breaks every action.

**Fix.** Emit the pinned snapshot in both virtual modules (`virtual:playwright-lite-injected` and `virtual:playwright-lite-evaluation`), taken when the adapter module evaluates. The pinned fallback semantics apply: use the live global when it is still valid, and the snapshot otherwise. Consider adding `URL` and `Date` for the protocol serializer, and state that addition as a difference from pinned. Then check whether the adapter's own `src/` code needs the same protection. The prototype, which bound only the pinned names, passed 7 tests without touching `src/`:

- `elementhandle-click.spec.ts > should work with Node removed`
- `elementhandle-misc.spec.ts > should fill input when Node is removed`
- `locator-click.spec.ts > should work with Node removed`
- `locator-misc-1.spec.ts > should fill input when Node is removed`
- `page-click.spec.ts > should click the button if window.Node is removed`
- `page-select-option.spec.ts > should work when re-defining top-level Event class`
- `page-wait-for-selector-1.spec.ts > should work with removed MutationObserver`

**Size.** Small runtime ticket (`fix:`). No ledger change is needed unless `URL` and `Date` are added.

### 4. Pinned error text and `apiName:` prefix for query and state errors (bug, ≤ 7 tests)

**Pinned behaviour.**

- Every public call's error is prefixed with the API name: `e.message = apiZone.apiName + ': ' + e.message` ([`packages/playwright-core/src/client/channelOwner.ts#L207-L208`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/client/channelOwner.ts#L207-L208)). That gives, for example, `elementHandle.$eval: …`.
- `$eval` with no match throws `Failed to find element matching selector "${selector}"` ([`server/frames.ts#L909`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/frames.ts#L909)).
- A detached element throws `Element is not attached to the DOM` ([`server/dom.ts#L970-L972`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/dom.ts#L970-L972)).
- An invisible target logs `  element is not visible` in the call log ([`server/dom.ts#L343`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/dom.ts#L343)).
- A non-string selector fails protocol validation with `selector: expected string, got object` (the validator in `playwright-core/lib/coreBundle.js`, pinned 1.62.1).

The adapter uses its own texts instead: `No elements found for locator …` (`src/page.ts:507`), `Element is not connected` (`src/page.ts`, more than ten sites), `select text: Timeout … Element is not visible` (`src/page.ts:1296`). **Fix.** Replace these texts with the pinned ones. Give every `ElementHandle` member the `elementHandle.<member>:` prefix, as the `Page` and `Locator` actions already carry `page.`/`locator.`. Validate the selector type before resolving it.

**Size.** Medium (`fix:`). Nothing breaks on the text change alone, but `Element is not connected` is matched at `src/page.ts:1017`, so the internal retry checks need updating together with it.

### 5. Pinned `waitForSelector` option validation (bug, 6 tests)

**Pinned behaviour.**

- `visibility` throws `options.visibility is not supported, did you mean options.state?`.
- `waitFor` other than `'visible'` throws `options.waitFor is not supported, did you mean options.state?`, and `waitFor: 'visible'` is tolerated ([`client/frame.ts#L239-L242`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/client/frame.ts#L239-L242), repeated server-side at [`server/frames.ts#L835-L841`](https://github.com/microsoft/playwright/blob/26a9e470a7b3c7822084b09fb7f13902c5f37b51/packages/playwright-core/src/server/frames.ts#L835-L841)).
- An unknown `state` throws `state: expected one of (attached|detached|visible|hidden)`.

`assertWaitForSelectorOptions` (`src/page.ts:5495-5515`) rejects every unknown key as `Unsupported waitForSelector option: <key>`, and a bad state as `Unsupported waitForSelector state: <state>`.

**Fix.** Check `visibility` and `waitFor` first, with the pinned text. Let `waitFor: 'visible'` through. Use the pinned `state:` message. Keep this package's rejection of every other unknown key, and state `waitFor: 'visible'` as the one pinned exception in `tests/contract/rules/option-validation.test.ts`.

**Size.** Small (`fix:`).
